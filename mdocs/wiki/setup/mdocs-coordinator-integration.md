## What mdocs is here

`harness-mdocs` 2.1.0 (npm devDependency, CLI at `./node_modules/.bin/mdocs`) provides project memory: initiatives in `mdocs/initiatives/`, durable wiki pages in `mdocs/wiki/<category>/`, workflow state in `mdocs/.workflow-state.json`, and an NDJSON `mdocs/audit.log`. Full command/tool reference: `node_modules/harness-mdocs/docs/agent-manual.md`.

This repo is driven by **docker-agent** (see `docker-agent.yaml`), which is *not* a native mdocs surface — there are no enforcement hooks, so the workflow contract is followed as **prompt discipline**, not host gating.

## Operating model (decided 2026-10-10: A1 + B1)

- **A1 — coordinator mutations via builder.** The root coordinator has no shell tool (toolsets: think, todo, filesystem). It reads `mdocs/` files directly and routes every CLI mutation through the `builder` sub-agent with exact commands.
- **B1 — sub-agents get no direct mdocs access.** The coordinator curates relevant wiki/initiative content and injects it into sub-agent task prompts (sub-agents start with fresh sessions). Only `builder` runs mdocs CLI commands, exactly as specified by the coordinator.

## Coordinator session checklist

1. Read `mdocs/.workflow-state.json` + `mdocs/initiatives/INDEX.md` directly (no shell needed).
2. Non-trivial work → `initiative.create` (via builder), then `mdocs resume <id>` to activate.
3. Advance steps in order (`mdocs step ...`): UNDERSTAND → DISCOVER → CONTEXT → PLAN → EXECUTE → VERIFY → REPORT → COMPLETE. No skipping; the engine rejects jumps.
4. Log progress after substantial actions: `initiative.update` with top-level `progressNote` (metadata changes go under `updates`; `objective`/`plan` are not updatable).
5. If files under `mdocs/` were ever hand-edited, run `mdocs command index.sync` before validating.
6. Link stable learnings first (`wiki.link`, `{"initiativeId":"...","wikiSlug":"setup/page-id"}`), *then* run `mdocs validate --human` — a wiki page declaring `related_initiatives` without the reciprocal initiative link fails graph validation, so validating before linking reports a false error.
7. `initiative.done` only after verification; consider `lifecycle.graduate` for big learnings.

## Command cheat sheet (run via builder)

```bash
./node_modules/.bin/mdocs status
./node_modules/.bin/mdocs resume <id>
./node_modules/.bin/mdocs step <STEP>
./node_modules/.bin/mdocs validate --human
./node_modules/.bin/mdocs command initiative.create --json '{"id":"...","title":"...","objective":"...","plan":["..."],"tags":["..."]}'
./node_modules/.bin/mdocs command initiative.update --json '{"id":"...","updates":{"nextAction":"..."},"progressNote":"..."}'
./node_modules/.bin/mdocs command wiki.link --json '{"initiativeId":"...","wikiSlug":"setup/..."}'
./node_modules/.bin/mdocs command index.sync
./node_modules/.bin/mdocs command initiative.done --json '{"id":"..."}'
```

## Guardrails

- Never hand-edit generated `INDEX.md` files; use `index.sync` / `mdocs index repair`.
- Keep sub-agent task prompts self-contained (absolute paths, curated memory excerpts) — they cannot see the coordinator's session.
- Long wiki content is written as a file by the coordinator (filesystem tool) in the flat-v1 format shown by existing pages, then reconciled with `index.sync` + `validate`; short mutations always go through the CLI.
- Upgrade paths if round-trips become a bottleneck: A2 = add `shell` toolset to root in `docker-agent.yaml`; A3 = wire the `mdocs mcp` stdio server if docker-agent gains MCP toolset support.
